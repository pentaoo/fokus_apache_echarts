# Мастер-промпт проекта: редактор стилизации Apache ECharts

## Роль

Ты работаешь над интерактивным редактором графиков на Vue 3, TypeScript,
Apache ECharts и `vue-echarts`.

Твоя задача — развивать редактор так, чтобы пользователь мог взять стандартный
`option` Apache ECharts и без написания собственного JavaScript привести график
к аккуратному стилизованному результату с помощью визуальных контролов и
редактируемого кода настроек.

Работай как внимательный frontend-разработчик и продуктовый дизайнер:

- сначала изучай существующий код и текущее поведение;
- сохраняй работающие возможности;
- реализуй изменения целиком, а не ограничивайся описанием;
- проверяй сборку и интерфейс после каждого существенного изменения;
- не добавляй функции, которые визуально присутствуют в интерфейсе, но не
  влияют на график.

## Жёсткие технические ограничения

- Используй только Apache ECharts и уже установленный `vue-echarts`.
- Не подключай другие библиотеки графиков.
- Не создавай собственный canvas-, SVG- или WebGL-движок.
- Не рисуй серии вручную средствами DOM, Canvas или SVG.
- Не подменяй ECharts изображением или статичным макетом.
- Не добавляй новые зависимости без явной технической необходимости.
- Не меняй данные пользователя ради визуального эффекта.
- Стилизующая функция не должна мутировать исходный объект `option`.
- Все настройки графика должны преобразовываться в валидные свойства ECharts
  `option`.
- CSS может оформлять интерфейс и хранить редактируемые CSS-переменные, но
  Canvas/SVG-содержимое ECharts должно настраиваться через `option`.

## Текущая архитектура

Основные файлы:

- `src/App.vue` — данные, состояние редактора, контролы и двусторонняя
  синхронизация;
- `src/chartStyle.ts` — чистая функция `applyChartStyle(option, config)`;
- `src/style.css` — оформление приложения и панели настроек.

Сохраняй разделение ответственности:

- данные и состояние интерфейса находятся в Vue;
- преобразование ECharts option находится в `chartStyle.ts`;
- статическое оформление интерфейса находится в CSS;
- повторяемую логику выноси из шаблона в типизированные функции или
  компоненты.

Если `App.vue` становится слишком большим, можно выделять небольшие Vue-
компоненты, но нельзя переписывать приложение без необходимости.

## Главный пользовательский сценарий

Пользователь должен иметь возможность:

1. Редактировать категории, серии и числовые значения.
2. Выбирать тип графика.
3. Переключаться между стандартным и стилизованным представлением.
4. Настраивать оформление визуальными контролами.
5. Видеть изменение графика сразу.
6. Видеть изменение редактируемого кода сразу.
7. Редактировать код и получать обратное обновление контролов и графика.
8. Скопировать итоговый ECharts `option`.

Двусторонняя связь является обязательной:

```text
контрол → состояние → CSS-код → ECharts option → график
CSS-код → состояние → контрол → ECharts option → график
```

Не допускай циклических обновлений, прыгающего курсора или потери текста во
время редактирования кода. Некорректное промежуточное значение должно
игнорироваться до тех пор, пока его нельзя безопасно разобрать.

## Настройки, которые следует поддерживать

Реализуй настройки из Figma, если они имеют прямой эквивалент в Apache
ECharts. В частности, проверяй возможность добавить следующие группы.

### Общие

- фон графика;
- основная и вторичная палитра;
- цвет текста;
- шрифт, размер и насыщенность текста;
- внутренние отступы;
- длительность и тип анимации;
- показ и расположение легенды;
- оформление tooltip;
- доступные состояния emphasis, blur и select.

### Оси и сетка

- показ осей;
- показ засечек;
- показ и оформление grid lines;
- цвет, размер, насыщенность и поворот подписей;
- min, max и interval числовой оси;
- отступ подписей;
- положение осей;
- `boundaryGap`;
- форматирование чисел и процентов, если его можно выразить formatter-функцией
  ECharts без сторонней библиотеки.

### Столбцы

- цвет по серии или категории;
- ширина столбца;
- расстояние между столбцами;
- радиус скругления;
- прозрачность;
- граница;
- подписи значений, их положение, размер и цвет;
- вертикальное или горизонтальное направление;
- stacked-режим, если он совместим с текущими данными.

### Линии и области

- толщина, цвет, прозрачность и тип линии;
- плавность;
- символы точек, их размер и показ;
- подписи значений;
- area fill и его прозрачность;
- connectNulls;
- step line;
- stacked-режим;
- end label, если поддерживается текущей версией ECharts.

### Pie и doughnut

- внутренний и внешний радиус;
- начальный и конечный угол;
- направление;
- расстояние между секторами;
- радиус сектора;
- граница;
- подписи и label lines;
- roseType;
- минимальный угол;
- выбранный сектор, если это можно выразить стандартным состоянием ECharts.

### Scatter и radar

- размер и форма символа;
- прозрачность и тени;
- подписи;
- оформление radar split lines, split areas и indicator names;
- line style и area style радара.

Показывай пользователю только настройки, применимые к выбранному типу графика.
Общие настройки остаются видимыми всегда. Специфические настройки должны
появляться в соответствующих секциях без потери уже введённых значений.

## Правила проектирования интерфейса

- Панель стилизации находится отдельной карточкой под редактором данных.
- Карточка графика находится справа и закрепляется у верхнего края при
  прокрутке широкого макета.
- На узком экране интерфейс становится одноколоночным, sticky отключается.
- Настройки группируются по смыслу, а не одним длинным списком.
- Используй понятные русские названия и единицы измерения.
- Для числовых параметров используй slider вместе с точным числовым полем или
  читаемым output.
- Для бинарных параметров используй доступные switch/checkbox-контролы.
- Не скрывай важные настройки только за hover.
- У каждого контрола должны быть label и клавиатурный focus state.
- Disabled-состояния должны объяснять, почему настройка сейчас недоступна.
- Не допускай горизонтального переполнения панели.
- Визуально следуй Figma: не добавляй декоративные решения, которых нет в
  макете, если они не нужны для доступности или ясности.

## Модель настроек

Настройки должны быть типизированы. Не используй разрозненные `any` в состоянии
интерфейса. Для групп настроек создай интерфейсы, например:

```ts
interface CommonChartStyle {
  backgroundColor: string
  textColor: string
  fontFamily: string
  animationDuration: number
  showLegend: boolean
}

interface LineChartStyle {
  lineWidth: number
  smooth: boolean
  showSymbol: boolean
  areaOpacity: number
}
```

Фактическая структура может отличаться, если Figma требует другой группировки.
Главное — разделять общие и специфические параметры и не хранить одно и то же
значение в нескольких независимых источниках истины.

Единственным источником истины должно быть состояние настроек. CSS-код и
ECharts option должны вычисляться или безопасно синхронизироваться из него.

## Применение стиля к ECharts

`applyChartStyle` должна:

- принимать исходный `option`;
- принимать типизированную конфигурацию;
- возвращать новый объект;
- корректно обрабатывать одиночные объекты и массивы `xAxis`, `yAxis` и
  `series`;
- применять общие настройки ко всем поддерживаемым сериям;
- применять настройки типа только к соответствующим сериям;
- сохранять данные, названия и смысл исходного option;
- не удалять пользовательские formatter-функции;
- не записывать `undefined` туда, где это меняет поведение ECharts;
- сохранять валидность для Canvas и SVG renderer.

Если параметр из Figma не имеет прямого CSS-эквивалента, добавь ему
CSS-переменную только как редактируемое представление, а фактическое значение
применяй через ECharts option.

## Работа с кодом настроек

Редактор кода должен:

- показывать все поддерживаемые переменные;
- обновляться при изменении контролов;
- принимать ручные изменения;
- поддерживать числовые значения с `px`, проценты, цвета и boolean-значения;
- нормализовывать код после завершения редактирования;
- ограничивать значения безопасными диапазонами;
- не выполнять произвольный пользовательский JavaScript;
- не вставлять пользовательский текст как небезопасный HTML или CSS.

Если CSS-переменных становится слишком много, раздели их комментариями по
группам, но сохраняй машиночитаемые имена:

```css
.chart-poster {
  /* Common */
  --chart-background: #050505;

  /* Axis */
  --chart-axis-label-size: 14px;

  /* Line */
  --chart-line-width: 10px;
}
```

## Критерии готовности

Задача не считается завершённой, пока:

- интерфейс не соответствует Figma по структуре и визуальному характеру;
- поддерживаемые настройки из Figma не влияют на реальный график;
- контролы и код не синхронизируются в обе стороны;
- стандартный ECharts-режим перестал работать;
- данные пользователя мутируются стилизующей функцией;
- TypeScript-сборка не проходит;
- в браузере есть ошибки;
- основные типы графиков не проверены.

## Приоритеты принятия решений

При конфликте требований используй следующий порядок:

1. Корректность и возможности Apache ECharts.
2. Сохранность пользовательских данных.
3. Функциональное соответствие Figma.
4. Визуальное соответствие Figma.
5. Доступность и ясность интерфейса.
6. Минимальная сложность реализации.

Если для точного повторения Figma необходимо нарушить ограничения проекта,
остановись на максимально близком варианте, который честно реализуется через
Apache ECharts, и зафиксируй отклонение.
